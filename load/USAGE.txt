영수증 비동기 처리 부하테스트

준비
  Docker 실행, Python 3.9 이상, k6 설치가 필요합니다. macOS k6 설치: brew install k6
  프로젝트 루트에서 아래 순서로 실행합니다.

  ./scripts/loadtest.sh up
  ./scripts/loadtest.sh prepare
  ./scripts/loadtest.sh smoke

up은 이미지를 빌드하고 독립된 receipt-loadtest 프로젝트를 실행합니다.
서버 주소는 http://127.0.0.1:19880 이며 기존 개발/운영 DB와 AWS를 사용하지 않습니다.
Grafana는 http://localhost:13000 에서 로그인 없이 읽기 전용으로 볼 수 있습니다.
InfluxDB와 Grafana도 같은 로컬 테스트 프로젝트에서 실행되며 외부로 공개하지 않습니다.
MySQL 8.4, Redis 7.2, S3Mock 5.2.3과 실제 로그인·세션·CSRF·업로드·Worker를 사용합니다.
추출기만 외부 API 대신 2초를 기다린 뒤 일정한 데이터를 반환합니다.
기존 기본 프로필의 Fake 추출기는 지연 없이 유지됩니다.

테스트 데이터
  load/generated/receipt.png: 800x1200, 약 2.9MB의 재현 가능한 노이즈 PNG
  load/generated/image.json: 크기, 생성 시드, SHA-256
  load/generated/admin.json: 테스트 환경 관리자
  load/generated/users.json: API로 발급한 테스트 직원 10명의 계정
  load/generated/grafana.env: 자동 생성한 Grafana 관리자 비밀번호 (일반 조회에는 불필요)

직원 수 조절: LOADTEST_USERS=20 ./scripts/loadtest.sh prepare
생성 데이터·비밀번호·결과는 Git에서 제외됩니다. 실사용 계정이나 영수증을 넣지 않습니다.
각 제출에는 고유한 PNG 메타데이터가 추가되어 이미지 SHA-256도 달라집니다.
파일명만 바꾸어 기존 중복 제출 경로를 측정하는 문제를 방지합니다.
이 이미지는 파일 처리용 합성 데이터이며 실제 영수증 인식 정확도를 검증하지 않습니다.

실행
  RATE=1 TIME_UNIT=2s DURATION=60s ./scripts/loadtest.sh run
    1번 시나리오: 2초마다 신규 영수증 1건을 60초간 제출합니다.

  ./scripts/loadtest.sh smoke
    5초마다 1건, 15초간 실행하는 소규모 기능 점검입니다. 성능 수치로 활용하지 않습니다.

  RATE=1 TIME_UNIT=1s DURATION=120s ./scripts/loadtest.sh run
    2번 시나리오: 초당 신규 영수증 1건을 2분간 제출해 기준 성능을 확인합니다.

  RATE=2 TIME_UNIT=1s DURATION=60s PRE_VUS=128 MAX_VUS=128 ./scripts/loadtest.sh run
  RATE=3 TIME_UNIT=1s DURATION=60s PRE_VUS=128 MAX_VUS=128 ./scripts/loadtest.sh run
    3번 시나리오: 초당 2건, 3건을 각각 1분간 제출합니다. 두 명령은 순서대로 실행하고
    이전 작업이 모두 완료된 뒤 다음 실행을 시작합니다. 완료를 기다리는 VU가 늘어도
    목표 제출률을 유지하도록 두 실행 모두 128개를 미리 준비합니다.
    이 값은 부하 발생기의 가상 사용자 수이며 Worker 동시 처리 수 4개와 다릅니다.

RATE는 영수증 제출 횟수입니다. 로그인·완료 조회를 포함한 전체 HTTP RPS와 다릅니다.
소수점 제출률은 RATE=1 TIME_UNIT=2s처럼 표현합니다 (2초마다 1건).
기본 설정: RATE=1, TIME_UNIT=1s, DURATION=60s, PRE_VUS=8, MAX_VUS=64,
          POLL_SECONDS=1, COMPLETION_TIMEOUT_SECONDS=60.
각 iteration은 제출 후 완료까지 조회합니다. k6가 독립적인 도착률로 새 iteration을 시작합니다.
응답이 느릴수록 더 많은 VU가 필요합니다. dropped_iterations가 발생하면 목표 제출률을
달성하지 못한 실행이므로 성공적인 처리량 결과로 사용하지 않습니다.
직원 계정은 VU에 순환 배정됩니다. 여러 VU가 한 직원의 세션을 공유할 수 있습니다.
장시간 시험은 세션 만료(기본 30분)와 fixture 규모를 별도로 고려해야 합니다.

지연과 Worker 동시 실행 수 변경
  LOADTEST_DELAY=2s LOADTEST_CONCURRENCY=4 ./scripts/loadtest.sh up
  LOADTEST_DELAY=2s LOADTEST_CONCURRENCY=8 LOADTEST_BATCH_SIZE=8 ./scripts/loadtest.sh up

up으로 실제 컨테이너를 갱신한 뒤 run을 실행해야 합니다.
Fake 지연은 Worker lease(기본 60초)보다 짧아야 합니다.
4개 Worker와 2초 지연이면 추출 대기만 고려한 상한은 약 2건/초입니다.
실제 처리에는 S3/이미지 검사/DB 등도 포함되어 이 값을 보장하지 않습니다.

결과: load/results/<고유 실행 ID>/
  summary.json      업로드/완료 시간 p95·p99, 성공·실패·시간 초과·제출 누락 수
  metrics.json      k6 원시 시계열 (긴 시험에서는 파일 크기가 커질 수 있음)
  queue.csv         약 2초 간격의 해당 실행 작업 수, 미완료 수, 구간별 완료 건수/초
  environment.json  실제 컨테이너 지연·동시 처리 수, 이미지 ID, Git 상태, 관측 실패 여부
  console.log       실행 로그

Grafana 확인
  실행이 끝나면 출력되는 Grafana 링크에는 실행 ID와 해당 시간 범위가 들어 있습니다.
  이 링크로 접속하면 시간이 지나도 해당 시험 결과를 확인할 수 있습니다.
  대시보드의 run_id로 실행을 선택하며, 접수/완료 수와 지연, DB 대기열을 확인합니다.
  최종 p95와 실패·시간 초과 합계 패널은 시험 종료 후 표시됩니다.
  최종 p95는 k6 요약값을 사용하며, 시계열 지연 차트는 10초 구간별 p95/p99입니다.
  접수 응답·최종 완료 확인·완료 조회 HTTP 응답을 각각 별도 그래프로 표시합니다.
  구간 값은 원시 측정값의 InfluxDB PERCENTILE로 계산하며, 전체 실행에 대한
  k6 백분위 값과 범위 및 계산 방식이 다릅니다. 구간 p95를 평균내어 전체 p95로 쓰지 않습니다.
  표본 수 패널을 함께 보세요. 1건/초에서는 구간당 약 10건뿐이라 p95/p99가
  최댓값과 같아질 수 있습니다. 표본이 없는 구간은 지연을 0으로 채우지 않습니다.
  계산 참고: https://docs.influxdata.com/influxdb/v1/query_language/functions/#percentile
  DB 작업 수는 약 2초 간격의 표본이므로 순간 최대치를 보장하지 않습니다.
  Grafana 전송이 필요 없는 실행은 LOADTEST_GRAFANA=0으로 지정할 수 있습니다.
  이 경우에도 JSON/CSV 결과는 남으며 이미 실행한 Grafana 컨테이너는 유지됩니다.
  summary.json에는 측정값과 설정만 남기며 로그인 세션은 저장하지 않습니다.
  같은 시각의 서로 다른 VU 표본을 보존하도록 load_vu를 InfluxDB 사용자 태그로 기록합니다.
  실행 종료 시 지연 표본 수와 성공/실패 카운터를 원시 결과와 대조합니다.
  불일치가 있으면 실행기는 실패를 반환하고 environment.json에 검증 결과를 남깁니다.

receipt_upload_ms는 제출 HTTP 응답까지, receipt_completion_ms는 제출 시작부터 완료를
클라이언트가 확인할 때까지입니다. 완료 지표는 조회 간격 지연을 포함하며 성공 건만 집계합니다.
따라서 p95만 보지 말고 실패·시간 초과·미완료 작업 수도 함께 확인합니다.
Job COMPLETED에 더해 기대한 추출 데이터까지 확인하여 이미지 품질 거절을 성공으로 세지 않습니다.
queue.csv의 완료 수는 DB 작업 완료 기준이며, k6 성공 수는 응답 데이터 검증까지 통과한 수입니다.
DB 관측 쿼리와 완료 조회도 시험 대상에 부하를 더하므로 비교 시 동일한 간격을 유지합니다.

기본 성공 조건: 접수 1건 이상, 모든 제출 최종 성공, dropped_iterations 0건.
성능 목표를 정한 뒤 UPLOAD_P95_MS=500 COMPLETION_P95_MS=5000처럼 추가할 수 있습니다.
이 숫자는 예시이며 현재 성능을 보장하는 기준이 아닙니다.
이전 실행의 대기/처리 중 작업이 있으면 다음 실행을 막아 시험 간 영향을 줄입니다.

비교할 때
  같은 장비, 이미지 크기, 지연, 제출률, 조회 간격을 유지하고 한 번에 한 요소만 변경합니다.
  준비 실행과 측정 실행을 구분하고 동일 조건에서 반복 측정합니다.
  S3Mock/Fake 환경 결과를 실제 AWS S3/OpenAI 처리 성능으로 표현하지 않습니다.
  현재는 로컬 생성기와 서버가 같은 장비에 있으므로 고부하에서 생성기 자체가 한계일 수 있습니다.

상태 확인 / 종료
  ./scripts/loadtest.sh status
  ./scripts/loadtest.sh stats
  ./scripts/loadtest.sh down

down은 테스트 컨테이너만 종료하며 테스트 DB/이미지 볼륨은 유지합니다.
Grafana와 InfluxDB도 함께 종료하며, 대시보드와 지표 볼륨은 유지합니다.
up도 기존 데이터를 지우지 않습니다. 테스트 볼륨을 별도로 삭제한 경우에는 해당 환경의
load/generated/admin.json, users.json도 별도 보관 후 다시 생성해야 계정과 DB가 일치합니다.
운영용 scripts/deploy.sh와 혼용하지 않습니다.

자원 사용량을 함께 측정하기
  LOADTEST_RESOURCES=1 RATE=3 TIME_UNIT=1s DURATION=60s PRE_VUS=128 MAX_VUS=128 ./scripts/loadtest.sh run

resources.jsonl에 앱·MySQL·Redis·S3Mock의 Docker CPU/메모리/PID 표본을 기록합니다.
Docker stats 출력은 약 2초마다 보존합니다. CPU 100%는 논리 CPU 한 개 수준이며
100%를 넘을 수 있습니다. 메모리는 Docker CLI가 파일 캐시를 제외해 표시한 값이며
JVM heap 크기와 다릅니다. Docker CLI의 표시 정밀도를 그대로 사용합니다.
측정 방법: https://docs.docker.com/reference/cli/docker/container/stats/

db-connections.jsonl은 약 2초마다 앱 IP의 MySQL 열린 연결/Sleep/SQL 실행 중 연결을
기록합니다. 관측용 DB 연결은 앱 연결 수에서 제외합니다. 서버 전체 연결에는 관측
연결이 포함될 수 있습니다. SQL 실행 중 수는 Hikari에서 빌린 연결 수와 다르며,
짧은 SQL은 표본 사이에 끝날 수 있습니다. Hikari 대기 시간/대기 스레드는 측정하지 않습니다.
Grafana의 컨테이너 자원과 DB 연결 패널은 자원 측정을 켠 실행에만 표시됩니다.

반복 비교는 4→6→8 / 6→8→4 / 8→4→6 순으로 각 설정을 3회 측정합니다.
각 실행에서 앱 컨테이너만 같은 이미지로 다시 생성하고, 같은 초당 3건·30초 준비
부하를 준 뒤 미완료가 0건일 때 초당 3건·60초를 측정합니다. 준비 부하는 별도 run_id로
보존하고 비교에서 제외합니다. 배치 크기 4, 지연 2초, 앱 메모리 1GiB는 유지합니다.
자원 비교는 첫 제출부터 60초 동안의 표본을 사용하고 종료 후 대기열 소진 구간은
따로 구분합니다. 전체 p95는 각 실행별로 계산하고, 반복 결과는 중앙값과 범위를
표시합니다. 서로 다른 실행의 p95를 평균내어 하나의 p95로 표현하지 않습니다.

반복 비교 결과 대시보드
  http://localhost:13000/d/receipt-worker-comparison/workers

실험별 완료 p95·CPU 평균·메모리 최대·대기열 최대의 3회 중앙값과 각 실행의
원래 수치를 표시합니다. 각 실행의 상세 시계열은 기존 receipt-loadtest 대시보드에서
run_id로 확인합니다. 비교표는 모든 반복이 끝나 검증된 뒤 별도로 기록합니다.
측정 원본과 실험 순서, 임시 설정 복원 여부는 load/results/workers-repeat-*/에 보존합니다.

동일 이미지 동시 제출 검증
  ./scripts/loadtest.sh duplicates

기존 부하테스트 서버와 계정을 사용합니다. 실제 AWS/OpenAI에 연결하지 않습니다.
10·50개 VU가 같은 이미지 1장을 동시에 제출하며 각 조건을 3회 반복합니다.
같은 요청 키 / 서로 다른 요청 키 / 요청 키 없음, 그리고 서로 다른 직원 2명의
같은 이미지 제출(50개 VU)을 검사합니다. 매 시험은 새 PNG marker를 사용합니다.
시험마다 처리가 끝난 뒤 동일한 VU 수로 다시 제출하여 상태가 유지되는지도 확인합니다.
총 21개 시험, 최초 690회 + 완료 후 690회 = 1,380회 제출입니다.

요청 수를 줄여 예비 실행하려면:
  python3 load/run-duplicates.py --repeats 1 --sizes 2

DB 기대값은 이미지당 Receipt 1개, Job 1개, attempt_count 1입니다.
Fake 추출 메서드 진입 로그도 1회인지 별도로 대조합니다. 해당 DEBUG 로그는
application-loadtest.yml에서만 켜집니다. 로그를 추가하기 전 이미지라면 먼저 up으로
테스트 앱을 다시 빌드해야 합니다. 기존 DB/이미지 볼륨은 유지됩니다.
같은 요청 키는 재전송으로 판단하여 DUPLICATE_DETECTED 감사 이벤트가 0개입니다.
다른 키/키 없음으로 여러 번 접수하면 중복 이벤트가 1개이며 NEEDS_REVIEW가 됩니다.
다른 직원의 제출은 409, 해당 영수증 조회는 404를 기대합니다.
두 직원이 1건씩만 제출하는 sizes=2 예비 검사는 소유자의 중복 제출이 없어 예외적으로
중복 이벤트 0개/AUTO_APPROVED를 기대합니다.
완료 후 재전송으로 Receipt/Job 버전이나 감사 이력, 실제 추출 횟수가 늘면 실패입니다.

검증기는 같은 읽기 전용 REPEATABLE READ 트랜잭션으로 관련 테이블을 조회합니다.
비동기 완료 전후의 서로 다른 스냅샷을 비교하여 오판하지 않기 위해서입니다.
load/results/dup-*/에 단계별 응답(상태/ID만), k6 원시 지표, 요약, DB 전후 스냅샷,
추출 진입 로그와 최종 validation.json을 저장합니다. 비밀번호/세션은 저장하지 않습니다.
