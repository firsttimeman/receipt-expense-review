# 직원 계정·인증·영수증 권한 구현 작업

이 문서는 Your dot이 Codex Cloud에 전달할 구현 범위와 검증 기준이다.
문서가 저장되거나 GitHub에 올라가는 것만으로 실행 예약이 생성되지는 않는다.

## 저장소와 시작 지점

- 저장소: https://github.com/firsttimeman/receipt-expense-review
- 준비 브랜치: `codex/cloud-erp-setup`
- 준비 브랜치의 최신 커밋에서 구현 브랜치를 생성한다.
- `main`에는 준비 브랜치의 문서 이동과 도메인별 패키지 정리가 아직 포함되지 않을 수 있다.
- 앱 코드는 `com.example.receipt.domain` 아래 도메인별 구조를 유지한다.
- 하나의 회사가 내부 직원용으로 사용하는 ERP의 영수증 처리 모듈이다.

## 클라우드 환경 준비

Codex Cloud 환경에 위 저장소를 연결하고 준비 브랜치를 선택한다.
브랜치 선택 기능이 없으면 작업을 시작하기 전에 준비 브랜치를 fetch하고 해당 커밋에서 새 구현 브랜치를 만든다.

필요한 실행 환경은 JDK 17, Git, Bash, Python 3, Docker CLI 및 실행 가능한 Docker daemon이다.
Gradle은 저장소의 wrapper를 사용한다. 테스트 컨테이너 이미지 `mysql:8.4`,
`redis:7.2-alpine`과 Testcontainers가 필요한 이미지를 내려받을 수 있어야 한다.
Gradle 배포판 및 Maven Central 의존성 다운로드도 허용되어야 한다.

환경 설정 후 다음 명령을 실제로 실행하고 통과한 환경을 게시한다.

```bash
bash scripts/cloud/verify.sh
```

이 명령은 전체 테스트와 MySQL/Redis 통합 테스트 실행 여부를 확인한다.
Docker가 없으면 기존 `disabledWithoutDocker` 설정 때문에 테스트 일부가 건너뛰어질 수 있으므로,
Gradle의 성공 문구만으로 전체 검증을 완료했다고 보고하지 않는다.
클라우드 환경에서 Docker를 실행할 수 없으면 그 제약을 보고하고 환경 문제를 해결한다.
실행하지 않은 테스트를 통과했다고 기록하거나 테스트를 비활성화해서 우회하지 않는다.

테스트는 fake 추출기를 사용한다. 이 작업에는 실제 OpenAI API 키나 운영 데이터가 필요하지 않다.
애플리케이션 수동 실행이 필요하면 Docker Compose도 준비하고 다음을 실행한다.

```bash
docker compose up -d --wait mysql redis
RECEIPT_EXTRACTOR_PROVIDER=fake bash ./gradlew bootRun
```

## 구현할 1~3단계

### 1. 직원 계정과 역할

- `domain/employee`에 entity, model, repository, service, dto, controller를 필요한 만큼 구성한다.
- 직원 식별자, 로그인 ID, 비밀번호 해시, 이름, 역할, 활성 상태를 관리한다.
- 역할은 `EMPLOYEE`, `REVIEWER`, `ADMIN`으로 구분한다.
- 기존 데이터와 함께 적용할 수 있는 Flyway 마이그레이션을 추가한다.
- 로그인 ID 중복을 DB에서도 차단한다.

### 2. 계정 발급·비밀번호 설정·로그인

- 관리자가 직원 계정을 발급하고 직원이 자신의 비밀번호를 설정할 수 있게 한다.
- 최초 관리자 준비 절차를 제공하며 공용 기본 비밀번호를 코드에 넣지 않는다.
- Spring Security 기반으로 로그인, 로그아웃, 인증 상태 확인을 구현한다.
- 비밀번호는 적절한 단방향 해시로 저장하고 응답이나 로그에 노출하지 않는다.
- 비활성 계정의 인증과 접근을 차단한다.
- 웹 기반 내부 ERP에 맞는 인증 방식을 선택하고 선택 이유와 클라이언트 사용법을 기록한다.
- 이메일 발송 연동과 프런트엔드 제작은 이 작업 범위에 포함하지 않는다.

### 3. 영수증 소유자와 접근 권한

- 영수증 제출자는 서버가 인증된 직원 정보에서 결정한다.
- 직원은 본인 영수증만 조회하고 업무 상태가 허용하는 범위에서 수정한다.
- 검토 권한이 있는 직원만 대상 영수증의 검토·승인·반려를 수행한다.
- 검토자 식별자도 서버 인증 정보에서 결정하고 클라이언트가 임의로 지정하지 못하게 한다.
- 상세 조회, 수정, 승인·반려뿐 아니라 감사 이력 등 관련 API에도 같은 접근 범위를 적용한다.
- 동일 이미지 업로드나 멱등성 키 재사용 경로에서도 다른 직원의 영수증을 반환하지 않는다.
- 기존 소유자 없는 영수증은 임의의 일반 직원에게 배정하지 않고 명시적인 이관 정책을 적용한다.
- 현재의 `X-Company-Id` 헤더를 사용자 인증 근거로 사용하지 않는다.
- 회사별 테넌트 관리나 관련 없는 성능 개선으로 범위를 확대하지 않는다.

## 완료 기준

다음 시나리오를 자동 테스트로 검증한다.

1. 관리자는 직원 계정을 발급할 수 있고 일반 직원은 발급할 수 없다.
2. 비밀번호 설정 및 정상 로그인이 성공하며 잘못된 비밀번호와 비활성 계정은 거절된다.
3. 직원 A는 영수증을 제출하고 본인의 내역을 조회할 수 있다.
4. 직원 B는 ID를 알아도 A의 영수증과 감사 이력을 조회하거나 수정할 수 없다.
5. 인증되지 않은 요청과 일반 직원의 승인·반려 요청은 거절된다.
6. 권한 있는 검토자는 검토를 수행하며 감사 이력에는 실제 로그인한 검토자가 기록된다.
7. 다른 직원이 같은 파일이나 멱등성 키를 사용해도 기존 영수증 소유자의 데이터가 노출되지 않는다.
8. 기존 및 새 Flyway 마이그레이션과 영수증 처리 회귀 테스트가 실제 MySQL/Redis 환경에서 통과한다.

구현 후 `bash scripts/cloud/verify.sh`를 실행하고 실제 테스트 수, 실패 수, 건너뛴 수를 기록한다.
README의 구현 현황, 로컬 계정 준비 방법, API 호출 예시를 실제 동작에 맞게 갱신한다.
최종 결과는 변경 코드, 테스트 결과, 남은 제약과 함께 검토 가능한 브랜치 또는 초안 PR로 제공한다.
PR을 만들었다면 작업에 연결하고 자동 병합하거나 운영 배포하지 않는다.
