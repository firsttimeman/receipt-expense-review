검토일: 2026-09-28 · 기준 커밋: `bac21cb` · 관점: 개인 개발 Java/Spring 백엔드 포트폴리오

현재 상태는 **핵심 기능과 동시성·장애 복구 설계를 갖춘 백엔드 MVP**다. 이력서에서 설명할 기술적 소재는 충분하다. 다음 투자 지점은 업무 상태의 정확성, 운영 가능한 경계, 성능·품질 주장의 재현성이다. 실제 서비스 운영 경험이나 실사용 성과는 저장소만으로 확인되지 않는다.

## 3. 이력서에서 살릴 강점

### 접수 트랜잭션과 외부 호출의 분리

Receipt·Job·멱등성 기록·감사 이벤트를 한 트랜잭션으로 저장하고, 외부 추출은 Worker가 별도로 수행한다. 네트워크 호출 동안 DB 트랜잭션을 유지하지 않는 이유와, 서버 중단 후 어떤 데이터로 복구하는지 설명할 수 있다.

근거: [ReceiptPersistenceService](../src/main/java/com/example/receipt/domain/receipt/service/ReceiptPersistenceService.java), [ReceiptJobClaimService](../src/main/java/com/example/receipt/domain/extraction/service/ReceiptJobClaimService.java).

### 중복·경합에 대한 방어 계층

동일 이미지 Redis 락, MySQL 유니크 제약, 검수 시 JPA 버전, Worker Claim Token은 각각 다른 경합을 다룬다. 각 장치가 방지하는 문제와 보장하지 못하는 범위를 구분해 설명하면 강점이 된다. Claim Token은 오래된 Worker의 결과 반영을 막지만 외부 AI 호출을 정확히 한 번으로 보장하지는 않는다.

### 병목 발견과 개선의 연결

성능 기록에는 동일 이미지 락 경합과 polling 대기로 인한 소비량 제한을 발견하고, 빠른 중복 응답 경로와 즉시 작업 보충으로 개선한 과정이 있다. 단순한 기술 나열보다 문제·가설·변경·검증을 보여주는 사례다.

현재 MySQL 큐 선택도 설명 가능한 결정이다. MySQL 공식 문서에서도 SKIP LOCKED를 여러 세션이 접근하는 큐 형태 테이블의 경합 완화 용도로 설명한다. 이 문서는 현재 구현의 처리량이나 장애 내성을 대신 증명하지는 않는다. [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).

## 4. 우선 수정할 경계 조건

### A. 필수 데이터가 없는 영수증을 승인할 수 있음 — 재현 확인

추출 실패로 `currentData=null`, `MANUAL_ENTRY`가 된 영수증에 승인 요청을 보내면 HTTP 200과 `APPROVED`가 반환된다. `decide()`는 재촬영·판독 불가 상태만 별도로 막고, 승인에 필요한 상호·날짜·총액을 확인하지 않는다.

- 영향: 증빙 데이터가 없어도 최종 승인된 경비가 만들어진다.
- 개선: 승인 필수 조건을 별도로 정의한다. 데이터 누락·금액 무효 같은 승인 차단 조건과, 한도·주말 사용처럼 권한 있는 검수자가 사유와 함께 예외 승인할 조건을 구분한다. 반려는 별도 전이 규칙을 적용한다.
- 완료 기준: 필수값 누락 승인 거부, 값 보완 후 승인 성공, 정책 예외 승인 시 권한·사유·감사 기록 검증.

근거: [ReceiptCommandService](../src/main/java/com/example/receipt/domain/receipt/service/ReceiptCommandService.java).

### B. 회사별 접근 제어와 검수자 신원 확인이 없음 — 재현 확인 및 알려진 미구현

A 회사 영수증을 조회하면서 `X-Company-Id: company-b`를 전달해도 A 회사 데이터가 HTTP 200으로 반환된다. 조회·수정·결정·감사 조회는 ID 중심이며, `reviewerId`도 요청 본문 값을 신뢰한다. README에도 인증·권한 미구현이 명시돼 있다.

- 개선: 인증된 사용자로부터 회사·검수자 정보를 결정하고 모든 조회/변경 경로에 회사 범위를 적용한다. 제출자와 검수자 권한을 나누고 운영 지표 접근도 제한한다.
- 완료 기준: 다른 회사의 조회·수정·승인·감사 조회 모두 차단되고, 검수 권한이 없는 사용자의 결정 요청이 거부됨.
- 우선순위: 외부 공개나 실제 데이터 사용 전에 완료할 항목.

근거: [ReceiptController](../src/main/java/com/example/receipt/domain/receipt/controller/ReceiptController.java), [ReceiptQueryService](../src/main/java/com/example/receipt/domain/receipt/service/ReceiptQueryService.java).

### C. 멱등성 키와 요청 내용의 관계가 불완전함 — 두 시나리오 재현 확인

1. 같은 키에 서로 다른 파일을 보내도 처음 영수증을 성공 응답으로 돌려준다. 요청 내용 불일치를 감지하지 않는다. 이를 허용할지 거절할지 계약을 명시해야 한다.
2. `key-1 + 이미지 A` 접수 후 `key-2 + 이미지 A`를 보내면 기존 영수증을 반환하지만 key-2는 저장하지 않는다. 이후 `key-2 + 이미지 B`는 새 영수증을 만든다. 같은 키가 이전 응답과 다른 리소스로 연결될 수 있다.

- 개선: 회사·키·요청 해시·영수증의 연결을 원자적으로 저장하고 내용 불일치는 명시적 충돌로 처리한다. 동일 이미지로 합쳐지는 경로에서도 키의 계약을 유지한다.
- 완료 기준: 같은 키/같은 파일, 같은 키/다른 파일, 다른 키/같은 파일, 동시 요청 네 조합 검증.

근거: [ReceiptUploadService](../src/main/java/com/example/receipt/domain/receipt/service/ReceiptUploadService.java).

### D. 반복되는 Lease 만료에는 종료 상한이 없음 — 재현 확인

최대 3회 처리는 `ExtractionException` 경로에 있다. Lease 복구는 횟수 확인 없이 QUEUED로 돌린다. 만료·복구를 4번 반복한 후 5번째 선점이 가능함을 확인했다. Worker의 예상하지 못한 런타임 오류도 이 복구 경로를 사용한다.

- 영향: 반복 실패 작업이 계속 슬롯과 자원을 소비할 수 있다. 문서의 ‘최대 3회’는 모든 실패 경로의 상한이 아니다.
- 개선: 외부 호출 실패와 Worker 복구의 횟수/시간 예산을 정의하고, 초과 작업을 FAILED 또는 별도 수동 처리 대상으로 격리한다. 운영자가 사유를 확인하고 재실행하는 경로도 마련한다.
- 완료 기준: 반복 만료, 반복 내부 오류, 재선점 후 오래된 결과 반영 거부를 함께 검증.

근거: [ExpiredJobRecoveryService](../src/main/java/com/example/receipt/domain/extraction/service/ExpiredJobRecoveryService.java), [ReceiptExtractionProcessor](../src/main/java/com/example/receipt/domain/extraction/service/ReceiptExtractionProcessor.java).

### E. 중복 업로드가 이미지 품질 상태를 바꿈 — 재현 확인

판독 불가 파일을 처리해 UNREADABLE로 만든 뒤 같은 파일을 다시 제출하면, 데이터 수정 없이 MANUAL_ENTRY로 바뀐다. 중복 처리에서 품질 상태를 유지하지 않고 데이터 규칙으로 다시 라우팅하기 때문이다. A의 승인 조건 누락과 결합하면 품질 때문에 거부됐던 승인이 가능해진다.

- 개선: 중복 플래그와 품질 상태의 관계를 정의하고, 수정·재촬영 없이 품질 상태가 바뀌지 않도록 전이 규칙을 적용한다.
- 완료 기준: UNREADABLE·NEEDS_RECAPTURE 상태에서 재업로드해도 의도한 상태가 유지됨.

근거: [ReceiptPersistenceService](../src/main/java/com/example/receipt/domain/receipt/service/ReceiptPersistenceService.java).

## 5. 고도화 방향

### 장애 처리와 다중 서버 실행

- HTTP 상태/네트워크 실패/응답 파싱 실패를 구조화해 재시도 가능한 오류와 영구 오류를 구분한다. 일시 오류에는 지수 백오프와 무작위 지연을 적용하고, 공급자 제한에 맞춘 호출 속도 제어를 검토한다.
- 현재 로컬 이미지 파일을 사용하므로 독립된 파일시스템을 가진 다른 서버의 Worker는 이미지를 읽을 수 없다. 다중 서버 실행을 목표로 한다면 공용 객체 저장소 또는 공유 스토리지와 보존·삭제 정책이 필요하다. 현재 테스트는 별도 호스트 간 이미지 접근을 입증하지 않는다.
- DB 저장 전에 파일을 쓰므로 DB 트랜잭션 실패 시 파일이 남을 수 있다. 고아 파일 정리와 디스크 사용량 관리가 필요하다.
- 이미지 디코딩 전 형식·픽셀 수 상한을 검사한다. 10MB 업로드 제한만으로 디코딩 메모리 사용량까지 제한할 수는 없다.

### 사용자가 끝까지 사용할 수 있는 검수 흐름

회사별 목록/상태 필터/페이지 조회, 권한 있는 원본 이미지 조회, 원본과 추출값 비교, 수정·결정·감사 이력까지 이어지는 작은 검수 화면을 만든다. 백엔드 직무라면 UI의 규모보다 업무 흐름을 직접 시연할 수 있는지가 중요하다. 실패 영수증의 보완 입력 또는 재접수 절차도 연결한다.

### AI 품질을 측정할 근거

저장소의 자동화 테스트는 주로 Fake와 로컬 HTTP 오류 응답을 사용한다. 실제 이미지에서 추출한 필드 정확도를 측정한 평가 데이터와 결과는 확인되지 않는다.

초기에는 사용 권한이 있고 민감정보를 제거한 영수증 30~50장 정도로 탐색 평가를 시작할 수 있다. 모델·프롬프트·평가 데이터 버전을 남기고, 필드별 정답률, 총액 오차, 추출 실패율, 잘못 자동 승인된 건수, 검수 전환율, 이미지당 비용과 지연을 기록한다. 소규모 결과에는 표본 수와 조건을 함께 표시한다. 규칙을 통과하는 일관된 오추출도 있을 수 있으므로 규칙 통과율을 인식 정확도로 대체하지 않는다.

### 운영 지표와 테스트 자동화

현재 Counter와 미완료 건수에 더해 접수→시작 대기시간, 추출시간, 접수→완료시간의 분포와 P95, 가장 오래 대기한 작업의 시간, 오류 유형별 실패, 실제 호출 횟수를 관측한다. 재시도·복구 지표를 기반으로 알림 조건을 정한다.

저장소에는 CI workflow가 없다. PR마다 단위/API 테스트와 MySQL·Redis 통합 테스트를 실행하고 결과를 보관한다. 현재 `disabledWithoutDocker=true` 설정으로 Docker가 없으면 핵심 통합 테스트가 건너뛰어질 수 있으므로, CI에서는 해당 테스트가 실제 실행됐는지도 확인해야 한다.

## 6. 성능 수치의 해석과 재현성

현재 문서에 기록된 성과:

| 시나리오 | 기록된 개선 | 설명할 범위 |
|---|---|---|
| 동일 이미지 200 VU × 30초 | 573.60 → 1,863.67 req/s, P95 824.38 → 242.90ms | 주로 중복 접수 경로의 처리 성능 |
| 고유 이미지 200건 | 전체 Job 완료 51.237 → 1.5757초 | 즉시 응답하는 Fake 환경에서 Worker 대기 제거 효과 |

이는 이번 검토에서 재측정한 수치가 아니다. 실제 AI 추출 200건이 1.6초에 끝난다는 주장을 뒷받침하지 않는다. 예를 들어 추출에 건당 5초가 걸리고 동시 처리 4개라면, 다른 병목이 없어도 소비량은 대략 0.8건/초다. 접수 API의 req/s와 완료 Job/s는 따로 제시해야 한다.

재현성 보완 사항:

- CPU·메모리·Docker 자원·JDK·DB 설정·Worker 동시성·이미지 크기·실행 커밋·워밍업·반복 횟수를 기록하고, k6 원본 결과를 보관한다.
- 고유 업로드 스크립트는 회사 ID와 VU별 이미지 바이트가 실행마다 같다. 같은 DB에서 기본값으로 다시 실행하면 신규 접수가 중복 조회로 바뀔 수 있다. 실행별 run ID로 데이터를 격리하고 생성 수를 확인한다.
- `check()`에는 신규 접수 조건이 있으나 `checks` threshold가 없다. HTTP 200 중복 응답도 HTTP 실패율은 낮게 유지될 수 있다. 신규 접수 검증이 실패하면 부하 테스트 자체가 실패하도록 threshold를 추가한다. k6 공식 문서도 check 실패만으로는 실패 종료 상태가 되지 않는다고 설명한다. [k6 공식 문서](https://grafana.com/docs/k6/latest/using-k6/checks/).
- Job 완료 여부를 확인하는 후속 검증을 스크립트화한다. 요청 수·고유 Receipt 수·Job 수·최종 상태·감사 이벤트를 함께 확인한다.
- 즉시 응답 Fake, 지연 Fake, 제한된 실제 AI 표본을 구분한다. 고유/중복 혼합, 장시간 유입, 429/5xx/타임아웃, Worker 중단을 포함한다.
- Grafana의 전후 성능 비교 3개 패널은 `vector(상수)`로 표시한 과거 기준값이다. 이미 설명에는 고정값이라고 쓰여 있다. 이를 실시간 P95·실시간 완료시간으로 소개하지 않는다.

근거: [PERFORMANCE_TEST_RESULTS.md](PERFORMANCE_TEST_RESULTS.md), [k6-unique-upload.js](../load/k6-unique-upload.js).

## 8. 이력서와 면접에 반영할 내용

이력서에는 개인 개발임을 밝히고 본인이 설계·구현·측정한 범위를 구체적으로 적는다. 아래 문구는 현재 코드와 저장된 측정 기록을 근거로 한 초안이며, 성능 항목은 측정 조건과 결과를 재확인한 뒤 사용하면 좋다.

> AI 영수증 검수 백엔드 개인 개발. Receipt·Job을 원자적으로 접수하는 MySQL 비동기 큐를 설계하고, SKIP LOCKED·Lease·Claim Token으로 작업 선점과 중단 후 복구를 구현.

> 동일 이미지 200 VU 부하 테스트에서 중복 처리 경로를 개선해 처리량 573.6→1,863.7 req/s, P95 824.4→242.9ms를 기록. Fake 추출기 환경에서 Worker 즉시 보충으로 200 Job 완료 시간을 51.2→1.58초로 단축.

> JPA 낙관적 락과 감사 로그를 적용하고, MySQL·Redis Testcontainers를 포함한 자동화 테스트로 중복 접수·재시도·작업 복구를 검증.

면접에서 준비할 설명:

1. Redis 락과 DB 유니크 제약을 함께 둔 이유 및 Redis가 없을 때의 대안과 측정 방법.
2. 외부 API 성공 직후 프로세스가 종료되면 무엇이 남고, 어떤 비용/중복이 발생할 수 있는지.
3. Lease와 Claim Token이 각각 해결하는 문제, 외부 호출의 정확히 한 번 실행을 보장하지 않는 이유.
4. 빠른 접수와 빠른 처리 완료의 차이, Fake 성능 수치를 실제 AI 처리량과 구분하는 방법.
5. 정책 위반의 예외 승인과 필수 데이터 누락을 다르게 다뤄야 하는 이유.
6. 최적화 전후의 실험 조건·원본 결과·반복 측정과 남은 병목.

README의 간결한 소개는 유지하고, 설계 결정·상태 전이표·실험 재현 절차·시연 자료는 별도 문서로 연결하는 방식이 적합하다. DTO에 남아 있는 학습 메모성 TODO는 이해를 정리한 설명이나 실제 작업 항목으로 바꾸면 공개 저장소의 완성도를 높일 수 있다.
